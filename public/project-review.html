SECTION 1

Project Overview

SSH Monitor UI (branded as Idle Testing Monitor) is a full-stack web application designed for Intel's hardware validation teams. Its purpose is to remotely connect to multiple servers via SSH, run PMUtil and Turbostat diagnostic commands on a repeating schedule, and surface the collected CPU C-state / power data in a live dashboard — all without needing to manually log into each machine.

Core use-case: An engineer wants to verify that several test systems enter deep CPU idle states (C6, PC6) during an "idle" soak test. They add each system's IP and credentials to the UI, set an idle interval and total duration, hit Add & Monitor, and the tool handles the rest — collecting, parsing, logging, and displaying data in real time.

The app is built entirely on open-source Node.js packages and runs directly on Windows (with start.bat) or any platform that has Node.js. No database is required — all persistent data is stored in log files under the logs/ directory.

SECTION 6

How It Works — Data Flow

1

User Adds a System

User fills in system name, IP, SSH credentials, idle time, and monitor duration on the main page and clicks Add & Monitor. The browser POSTs to POST /api/systems which registers the system in the in-memory Map and immediately starts monitoring.

2

Backend Starts the Monitoring Loop

startMonitoring() initialises all counters, marks status as running, and calls scheduleNextRun() to schedule the first data collection using setTimeout. The loop count and target runs are computed from the idle / duration settings.

3

SSH Connection & Command Execution

On each loop tick, collectOnce() opens a fresh SSH connection via ssh2. It executes the PMUtil command first, then the Turbostat command sequentially, capturing stdout from each. Each command has a 15-second timeout.

4

Parsing & Extraction

parseSockets() extracts the socket count from PMUtil output via regex. parseTurboStat() locates the header row containing CPU%c6 and Pkg%pc6 in the tabular output, then reads values from the first data row — this is the key metric for idle state validation.

5

Logging to File

Raw PMUtil and Turbostat output is appended to a per-system timestamped log file under logs/. Each block is prefixed with an ISO timestamp and a label like LOOP_3_PMUTIL, making logs human-readable and machine-parseable.

6

WebSocket Broadcast

After each collection, the backend calls broadcast() which sends two events to all connected browsers: a systemUpdate (summary stats) and a systemOutput (raw text). Both the main dashboard and any open live-output windows receive these in real time.

7

Loop Continues or Stops

After each successful collection, the loop counter increments and scheduleNextRun() is called again using the planned tick time (aligned to the original start time) to prevent drift. When loopCount >= targetRuns, the system is marked completed.

SECTION 11

SSH Resilience & Recovery Logic

One of the most important backend features is the automatic SSH recovery system:

!

SSH Failure Detected

If a connection attempt or heartbeat fails, sshFailureSince is set to the current timestamp. The timer is paused (elapsed time tracking excludes the pause duration).

↺

Retry Every 1 Second

probeSshRecovery() is called every 1 second using a short SSH_RECOVERY_RETRY_MS timeout. This aggressively probes for reconnection.

✓

Recovery Detected

On success, markSshRecovered() calculates the total pause duration, increments sshReattemptCount (if paused > 10 s), resets all failure flags, and logs a recovery message. The UI shows a green recovery banner for 8 seconds.

✗

1-Hour Timeout Limit

If SSH remains unreachable for more than 1 hour (SSH_MAX_RECOVERY_DURATION_MS), the system is permanently stopped with status error and the reason "SSH unreachable for over 1 hour".

A separate SSH heartbeat also runs every 5 seconds during normal operation to proactively detect SSH drops even between scheduled loops. This ensures failures are reported immediately without waiting for the next data collection.

Quick Start

1

Install dependencies

npm install — installs express, ssh2, ws, cors

2

Configure (optional)

Copy .env.example to .env and set SSH_USERNAME, SSH_PASSWORD, etc. Or set env vars inline.

3

Start the server

npm start (production) or npm run dev (nodemon watch mode). On Windows you can also double-click start.bat.

4

Open the UI

Navigate to http://localhost (or http://<your-ip>:PORT from another machine on the same network).

5

Add a system and monitor

Fill in the system name, IP, SSH credentials, set idle time and monitor duration, then click Add & Monitor. Watch data populate in the Active Summary table in real time.
